This feedback establishes that the changes did not eliminate the reported lag;

The owner then narrowed and clarified the symptom: a few seconds after closing
Storage, the idle home screen lags temporarily and eventually becomes smooth again.
Before opening anything, the home screen is fairly smooth. Do not describe this
as a persistent post-close slowdown. This is owner-reported timing, not a trace.
Storage's open/close lifecycle (native behavior and mod behavior), including delayed
or settling work proportional to inventory size, is the investigation scope. The
personal repair scan has no explicit Storage-open trigger, making it a weaker fit,
not excluded. The owner asks whether exceeding 400 items contributes. The latest
reviewed session reports 435 Storage and 35 Trash drawers; this demonstrates a large
view, not a measured performance threshold at 400. The native capacity limit and
its bypass must not be conflated with a demonstrated performance cliff.

Static tracing confirms the closed UI path hides controls and clears popup/focus
state, but retains the captured inventory view and does not stop iq_update from
calling iq_present on dispatched drawers. Conversely, the existing session logged
a native drawer callback at 15:48:39.544, before the first added-control creation
at 15:48:41.461. Therefore drawer callbacks cannot simply be assumed to start only
on opening Storage. Newly created control entities also persist after hiding;
their native update/render cost is not measured. No additional fix is justified
by this timing correlation alone. Next evidence should compare pre-open idle,
open/close, the delayed lag and recovery to smooth idle during an owner-run timing
capture, preserving scrolling and uncapped-storage protection. A count comparison
must account for both Storage and Trash; moving items between them does not reduce
the combined drawer count. No game or test was run by the agent.

## Scope

Mod-owned controls remember a successful hide and skip repeated guarded reads
and visibility writes until another show attempt. Show clears the hidden state
before creation/setup, so a partially completed show remains eligible for cleanup.
Actual renderer access still validates the current generation and vtable. Failed
validation does not mark a control hidden. Owner changes retain the existing hide
and reset behavior.

Drawer positioning, native updates, tooltip cleanup, input hooks, assets, installer
mapping and saved inventory are unchanged. This removes source-confirmed redundant
work; it is not proof of the cause of idle-house spikes or a measured FPS gain.

The control type and hide helper are shared with the existing lifetime fixture.
Its added cases cover repeated hides, show-state reset, absent/unreadable/recycled
objects and changed vtables. These assertions were added but NOT run. They do not
exercise the complete native show function or game scene transitions.
